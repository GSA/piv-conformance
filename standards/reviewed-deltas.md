# Reviewed PIV data-model deltas

Source/code review: 2026-10-02. Historical CCT: `90f754d785f7fe4ca9fb19e1c66102da0608447d`; candidate inspected: `7138183709374ff4d71f7dc9d67c64654c327532`. This is the implementation triage for PR #328. It covers all 18 candidate assertion groups, not every applicable requirement in the standards. “Reviewed” means compared with the cited publications and source; it does not mean independent or NIST approval. The initial review delivered no runtime behavior; implementation updates are recorded below.

**Objective:** modernize the existing CCT's applicable PIV data-model checks with the smallest justified changes, trace each changed behavior to an exact final requirement, and demonstrate it through the actual CCT execution path.

Normative change and implementation quality are separate questions. An existing requirement can have a CCT bug or missing evidence. Optional applicability is not a revision delta. Six candidate groups contain revision changes; twelve address existing requirements. These are mixed-size groups, not an atomic denominator or a completion percentage. The earlier nine-CHANGED/one-CONDITIONAL classification is superseded below.

The accurate scope statement is **“selected PIV data-model checks supporting applicable FIPS 201-3 requirements.”** A blanket FIPS 201-3 conformance claim is unsupported. Enrollment, issuance, lifecycle, physical printing, card-edge activation and Part 3 middleware qualification are not proved here. PIV-I needs a separately justified applicability profile.

## Package decisions and exit criteria

1. **Keep the six normative changes as scoped above; revise their implementation toward existing atoms.** Retain revision selection only for actual changed requirements. Fix B1/B2 in existing checks with explicit bug-fix provenance. Fix B3 in the engineering PR.
2. **Reuse tests for unchanged behavior; justify new production code individually.** The parallel `CurrentDataModel`, `CurrentCrypto`, `CurrentIdentity` and `CurrentBiometrics` helpers are not accepted as necessary merely because they have vectors. Avoid a second complete validator or parser by default.
3. **Hold incomplete scope out of delivered claims.** SAN holder linkage, issuer-key relationships, CMS/hash validation, full certificate profiles, biometric payloads, conditional objects and retired OID interoperability remain open. Synthetic path-policy evidence is not recovered provenance for the missing historical certificate corpus.
4. **Shrink the review package.** Keep this list, source references, focused implementation/tests and short reproduction instructions. Generate bulky historical inventories, modal-text indexes and reference comparisons as artifacts. Delivered 2026-10-05: inventories/comparisons now generate under ignored build/standards; repeated database-row lists were removed from the manifest, and the unused modal-text dump was removed. The generator defaults to UNREVIEWED; assertion counts cannot establish partial conformance. Two regenerations produced identical artifact hashes.
5. **Accept each delivered change only after** its exact source/applicability is linked, an existing CCT database row invokes the intended atom via the normal acquisition path, a positive input passes, an intended violation fails for the specific reason, and relevant regressions pass. A simulated acquisition path proves software execution, not physical-card qualification. Security alerts and PR checks must be verified on the final commit before external submission.

This first review supports a smaller implementation plan. It does not establish that the historical CCT was broadly nonconformant or that all final-standard deltas have been inventoried. Broader completeness requires a separate semantic audit, not counting generated records.
